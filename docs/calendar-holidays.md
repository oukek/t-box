# 节假日年度数据

农历、节气与节日名称由日历 contracts 中的 almanac 计算；休/班安排从数据库读取。月历、日期选择器、周日程和重复星期按钮均按「日一二三四五六」展示，存储的星期编号仍是 ISO 的周一=1、周日=7，已有重复规则不变。

## 数据与同步

应用自己的 `apps/calendar/server` 提供 TypeORM 实体、数据库迁移、同步服务、数据源适配器和后台路由。平台仅注册其实体、迁移及路由；AI 核心没有节假日业务。`calendar_holiday_years` 分开保存候选与已发布年度 JSON、版本、手动保护、最近检查、错误和来源。`calendar_holiday_settings` 保存同步开关，`calendar_holiday_audit` 记录同步和管理员变更。

默认数据源是 [NateScarlet/holiday-cn](https://github.com/NateScarlet/holiday-cn)，它根据国务院公告整理年度数据并保留 `papers` 官方原文链接。该项目属于第三方数据源，不是政府提供的官方 API。适配器位于 `holiday-provider.ts`，可替换数据源，不影响 API、界面或 AI 工具。初始化迁移仅导入此前核实的 2026 年安排，后续年度和变更不再随前端打包。

后台启动时检查上一年、本年和下一年，之后每 6 小时检查；成功年度 24 小时内不重复同步，失败年度最少间隔 1 小时重试。用户查看其他年度时按需同步。MySQL 命名锁防止多个 API 实例并发同步同一年，进程内请求也合并；关闭服务时取消网络请求并等待清理。网络有超时与 64 KiB 数据上限；GitHub 原始地址失败时尝试同一仓库的 jsDelivr 镜像，每个地址最多 6 秒。

同步校验年度、真实日期、重复日期、休班类型、政府公告链接和七类主要节假日覆盖。跨年通知允许涉及上年 12 月及下年 1 月。相邻年度中较新通知优先。未公布的空数据、404、网络或格式错误不清空已发布安排。第三方数据源可能遗漏普通周末连休；页面「休／班」只标记录中明确的安排，常规周末另以颜色区分。

## 管理后台

打开 `http://localhost:5175/#/holidays`。

- 同步年度：从数据源获取指定年度，手动保护的年度不会被覆盖。
- 同步配置：开关定期同步；选择校验通过后自动发布或人工审核发布。
- 查看／编辑：通过日期列表与「放假／调休上班」自定义下拉修改，保存草稿开启手动保护，但不影响现有发布。
- 发布候选：完整性校验通过后生效，前端和 AI 均读取已发布数据；仍保持手动保护。
- 恢复自动：解除保护，允许后续自动数据替换候选；自动发布开启时也会更新公开数据。
- 记录：查看近期操作类型、版本、时间及系统／管理员来源；数据库保存完整变更快照。

写入使用版本校验和事务，过期页面不能覆盖新版本。管理路由继承平台管理员登录、会话和 CSRF 校验，普通用户不能修改。

## 前端和 AI

登录用户通过 `GET /api/v1/calendar/holiday-years/:year` 获取公开快照（候选不返回）；日期详情接口和 `calendar_today`、`calendar_date_info` 后端工具组合数据库安排与农历信息。关闭前端不影响工具调用。

日历应用通过统一 SDK 缓存年度数据，打开时先恢复缓存，再按需更新（1 小时新鲜期）；失败保留旧缓存并提示。已经加载的页面在断网时仍显示缓存数据。完整的离线登录和应用启动不属于此缓存模块。前端刷新只重取后端公开数据；强制数据源同步仅管理员可操作。

未收录或未公布的年度仍显示农历、节气与节日名称，但不猜测放假调休。前端与 AI 一致使用 `scheduleKnown` 区分状态。

验证：`pnpm test:holidays` 检查真实 MySQL 的同步、候选／发布、失败保留、手动保护和版本冲突；单元测试检查来源校验、跨年覆盖、日期与星期顺序。测试只使用临时年度并清理，不修改真实年度安排。
