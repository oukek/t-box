# 方舟系统版本与统一更新方案

已有生产网页版、首次上线桌面与 PWA，请从[按顺序部署的操作手册](first-desktop-pwa-rollout.md)开始。

实施方案 · 2026-11-25。范围是方舟网页/PWA 主界面和 Tauri 桌面客户端。待办、电商助手等子应用沿用应用市场的发布流程。

## 发布 Intel 和 Apple 芯片 Mac 版

1. 在根目录 `release-versions.json` 填写高于线上版本的 `macos.core`。两种芯片共用这个版本。要一起发布网页里的下载入口，`ui` 也要高于当前线上 UI。
2. 把代码推到 GitHub，先运行[后端部署](https://github.com/oukek/t-box/actions/workflows/api-pm2.yml)，再运行[管理后台部署](https://github.com/oukek/t-box/actions/workflows/admin-oss.yml)。
3. 运行一次 [macOS 整包发布](https://github.com/oukek/t-box/actions/workflows/desktop-release.yml)。沿用已有的 Developer ID、Apple 公证账号及更新签名密钥。工作流逐个编译原生 arm64 和 x86_64，验证 DMG 中有 Applications 快捷方式、镜像与更新包中的应用签名一致，再将两份安装镜像与两份更新归档放入私有 OSS。全部成功后登记同一个候选。
4. 在管理后台「系统发布 → 桌面端」选 Apple 芯片或 Intel 下载待确认的体验版。打开 DMG，将 T方舟拖到 Applications，推出磁盘镜像，再从「应用程序」打开。仅 UI 的内部体验仍是带启动器的独立 ZIP，可按芯片下载。
5. 这次同时更新 UI 和核心时，在「系统发布 → 主界面」确认；仅更新核心时，在「桌面端」确认。正式用户可在网页「设置 → 系统版本」选择芯片下载。浏览器提供可靠的架构信息时标出推荐项；不确定时可在 Mac 的「关于本机」查看芯片或处理器。
6. 用已安装在「应用程序」的旧版本检查更新。确认「更新并重启」后，客户端按自身运行架构下载签名更新包，校验、安装并重启。仅 UI 更新沿用刷新流程。在 Intel 和 Apple 芯片真机分别核对版本和账号数据；历史单架构版本仍只提供原 Apple 芯片归档。无需运行 iOS 工作流。

### 05 本地复验

在安装 Xcode 命令行工具、Rust 和工作区依赖的 Mac 上，运行 `TBOX_UI_VERSION=1.1.16 pnpm desktop:build` 可生成本机架构的 `desktop/src-tauri/target/release/bundle/macos/T方舟开发版.app`。开发包使用独立应用标识及存储目录。示例版本用于本地验收；发布流水线应传后端预留的界面版本。核心版本在 `desktop/src-tauri/Cargo.toml` 的 `package.version` 填写。本地构建使用 ad-hoc 签名，对外分发的签名、公证及更新流程见后续步骤。

主界面随安装包提供。桌面壳默认从 `https://apps.tboxos.cn` 读取已安装子应用的制品；其他部署可在编译时设置 `TBOX_ARTIFACT_ORIGIN`、`VITE_API_BASE_URL`。首次下载逐文件验证 SHA-256 后启用，文件位于 `~/Library/Application Support/cn.tboxos.desktop/applications/<appId>/<digest>/`。各版本从独立的本机回环地址运行。资源离线可用范围取决于此前下载的版本；账号下的待办数据读写仍需要后端。

运行 `cargo test --locked --manifest-path desktop/src-tauri/Cargo.toml` 可复验损坏的新包被拒绝、旧包仍可离线打开及来源检查。图像验收使用独立应用标识和模拟账号；远端发布与真实微信登录留待部署环境验证。

### 06 签名更新的构建与对接

- 主窗口通过桌面核心检查渠道。编译时设置 `TBOX_UPDATE_ENDPOINT`、`TBOX_UI_PUBLIC_KEY`、`TBOX_CORE_PUBLIC_KEY`。后两项为 **两套独立** Tauri signer 密钥的 `.pub` 文件内容。客户端不接收页面传入的公钥或下载地址。仅 debug 构建允许使用本机回环 HTTP 做验收。
- 界面使用桌面模式构建。将构建时使用的同一版本传给 `node desktop/pack-ui.mjs desktop/dist 1.1.17 <输出文件>`，用界面私钥执行 `tauri signer sign`，登记包的 SHA-256 和生成的签名。签名覆盖界面版本、桥接协议和每个资源的内容。当前桌面桥接协议为 1。
- 核心使用 `bundle.createUpdaterArtifacts: true` 构建，并将核心公钥写入构建用的 `plugins.updater.pubkey`。客户端要求签名绑定目标版本；macOS 使用 Tauri 生成的 `.app.tar.gz` 与 `.sig`。Updater 签名负责验证更新包，面向公众分发的 Apple 签名与公证另行配置。
- 检查请求为 GET，含 `platform`、`arch`、`ui`、`core`。无更新返回 204；有更新返回以下结构。可省略无变化的组件。核心的 `endpoint` 指向该架构和版本对应的 Tauri Updater 清单。生产渠道配置与后台确认见第 07 项。

```json
{
  "id": "846bf75a-54cd-4295-9086-ca1e869c9ff0",
  "notes": "本次更新说明",
  "ui": {
    "version": "1.1.17",
    "digest": "<64 位小写 SHA-256>",
    "signature": "<界面包 .sig 内容>",
    "url": "https://<制品域名>/<不可变界面包路径>"
  },
  "core": {
    "version": "1.0.1",
    "endpoint": "https://<发布域名>/<不可变核心清单路径>"
  }
}
```

更新使用独立的原生状态记录。仅界面更新重载原窗口；含核心时先备齐并验签，再保存目标、安装并重启。新核心启动时核对实际版本，新界面挂载后通过原生握手确认。候选界面 25 秒内没有握手，或首次试运行中断后再次启动，会恢复上一份已验证的界面；该界面不可用时加载内置界面。核心二进制无法启动时仍需修复安装包。

### 07 发布操作与验收

首次生产签名请从[Apple 后台与 GitHub Actions 配置手册](macos-developer-id-signing.md)开始。

1. 先部署本次 API、迁移与管理后台。在后端配置 `TBOX_UI_PUBLIC_KEY`、`TBOX_CORE_PUBLIC_KEY` 为两套 Tauri signer 公钥文件的完整内容。自定义域名同步设置 `TBOX_DESKTOP_API_BASE`（含 `/api/v1`）。后端使用现有主站 OSS 凭证；私有下载通过一小时有效的 OSS V4 签名地址分发。
2. GitHub 的 `desktop-release` Environment 使用已有的 `DEPLOY_DOMAIN`、`OSS_REGION`、`APP_IMPORT_TOKEN`、OSS 访问凭证。将同一对公钥分别写入同名 Variables，将两个私钥文件内容分别保存为 Secrets `TBOX_UI_PRIVATE_KEY`、`TBOX_CORE_PRIVATE_KEY`，对应口令为 `TBOX_UI_KEY_PASSWORD`、`TBOX_CORE_KEY_PASSWORD`。正式向外分发 macOS 应用时配置 Apple Developer ID 签名与公证：Variable `APPLE_SIGNING_IDENTITY`、`APPLE_TEAM_ID`，Secrets `APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_ID`、`APPLE_PASSWORD`。生产核心工作流要求 Developer ID 身份，上传前验证归档内应用的签名、团队及公证票据。本地开发构建仍使用 ad-hoc 签名。
3. 首次用 macOS 整包建立基线。日常主界面构建同时登记网页与 Mac 签名包，后台填写一次更新内容。整包工作流在 UI 与线上同号时复用线上已批准的签名界面。
4. 在「应用管理 → 系统发布 → 主界面」（仅核心构建进入「桌面端」）检查组合，逐行填写更新内容并确认。后端复核 OSS 中的实际字节、两套签名、内置界面摘要、核心版本和 Mach-O 架构，然后在一个事务内切换生效记录。基线已变化的候选需要按新基线重建。「下载安装包」提供当前获批的核心归档，解压得到 `T方舟.app`；同一份归档也用于 Tauri Updater。渠道首次启用时需安装已内置正确公钥与检查地址的客户端。
5. 实际客户端用 `GET /api/v1/system-updates?platform=macos&arch=aarch64&ui=…&core=…` 检查。无更新或不支持的架构返回 204。已批准的安装包入口为 `GET /api/v1/system-updates/macos/<arch>/installer`。检测更新与安装入口均使用实际架构 `aarch64` 或 `x86_64`。首次安装包和更新包都在主站桶的私有 `desktop-candidates/<build>/<sha256>.*` 下，后台审核控制下载入口和版本可见性。

本地复验命令为 `MYSQL_DATABASE=t_box_test_desktop pnpm --filter @t-box/api exec tsx test/desktop-releases.integration.ts`，需可创建临时数据库的 MySQL 账号。另用两套临时密钥和真实 macOS 构建，经上传代码与后端完成三组发布：联合 1.1.17 / 1.0.2，仅界面 1.1.18，仅核心 1.0.3。最后一组直接使用前一组已批准的界面包。GitHub 和生产 OSS 验收由部署环境执行。

### 08 桌面自动检查与进度验收

启动后静默检查。窗口可见且在线时，每 30 分钟检查一次。回前台距上次成功检查超过 1 分钟可提前检查。网络失败从 1 分钟起退避，最长 30 分钟。恢复联网时补查并遵守失败退避，用户从设置手动检查可立即发起请求。多个触发共用进行中的请求。点「稍后」后，本次会话对同一发布不再自动弹窗，仍可从设置手动调出。

再次打开客户端会聚焦现有主窗口。开始下载前，宿主请求已连接且支持保存协商的子应用处理未保存内容。电商助手 1.3.4 会尝试保存当前项目，编辑弹窗尚有待确认内容时会阻止开始更新。采用旧 SDK 的子应用依赖用户先手动保存。新版本电商助手仍走子应用独立发布。

桌面端从原生任务恢复下载状态。合并更新时按后台验签后记录的实际制品字节数累计进度；没有可靠总量时展示当前阶段。桌面验收使用本机测试渠道、测试签名和 Apple Silicon 客户端。定时与失败退避使用模拟时钟，联网及前台事件由验收驱动触发。可运行：

```sh
node --test scripts/desktop-check.test.mjs
pnpm test:app-sdk
MYSQL_DATABASE=t_box_test_phase08 pnpm --filter @t-box/api exec tsx test/desktop-releases.integration.ts
cargo test --manifest-path desktop/src-tauri/Cargo.toml
```

## 1. 现状与版本来源

当前设置页读取 `appInfo.version`，它来自 Vite 注入的 `__APP_VERSION__`，正式构建使用后端预留的版本，网页本地开发默认取 `release-versions.json` 的 `ui`。主站正式构建同步使用预留的 UUID，本地构建自行生成 UUID，写入网页代码和 `web-version.json`，用来检测文件批次变化。旧工作流只传 UUID，导致设置长期显示同一个数字。无法仅凭现有 UUID 可靠还原历史语义版本，建议从下一次正式发布开始记录。

主站工作流把完整产物上传到主站桶的私有候选目录，向后端登记 SHA-256。管理员进入「应用管理 → 系统发布」确认后，后端复核产物并依次写入资源、首页、服务工作线程和版本标记。每个文件经 OSS 公开地址回读校验后继续；生产验收另查自定义域名和 CDN。

| 标识 | 作用 | 示例 |
| --- | --- | --- |
| 界面版本 | 方舟主界面实际运行的 HTML、JS、CSS 版本，网页、PWA、桌面均显示 | 0.2.4 |
| 桌面核心版本 | 实际运行的 Tauri 二进制版本，由客户端读取；网页/PWA 无此项 | 1.1.0 |
| 发布编号 | 后端为构建批次分配的 UUID，关联目标组件组合与更新说明 | 桌面计划的 `id` 对应候选的 `build` |

建议设置入口叫「系统版本」。普通用户看到界面版本；桌面版同时显示桌面核心版本。发布编号放在详情和反馈信息里。管理员维护两个组件版本，不需要再手填第三个“总版本”。壳单独更新时，设置里只有桌面核心版本变化。构建 UUID、Git commit、文件摘要用于识别和追踪产物，不用于判断版本大小。

网页和 macOS 在构建前按仓库声明的目标版本向后端预留。相同组件组合的最新待确认候选可同号重建。开始上线后该版本即受保护。

CI 将预留的界面版本和构建 ID 一起写入界面包与版本文件。壳版本写入 Tauri 打包配置和安装包元数据，CI 校验与预留记录一致。设置页读本机实际运行值；服务器目标只出现在「可更新到」一栏，下载完成或重启失败都不能提前显示已升级。

当前预留接口为 `POST /api/v1/system-builds/reserve`，数据库事务内按组件独立递增，首次界面从 0.1.0、核心从 0.0.0 起算。每个组件版本字符串最多 96 个字符。仓库与 Actions run ID 标识批次，同一批次须使用同一提交和版本选项；若已有新批次推进相同组件，旧批次重跑会被拒绝，避免旧版本重新覆盖线上入口。主站通过系统发布页确认上线，管理后台站点沿用独立 OSS 部署。

### 2.1 怎样设置版本号

在仓库根目录修改 `release-versions.json`，随代码一起提交。工作流从检出的提交读取对应字段。

| 发布内容 | 修改字段 | 操作入口 |
| --- | --- | --- |
| 网页、PWA 和 macOS 界面 | `ui` | 主界面构建（网页、PWA、Mac） |
| macOS 核心 | `macos.core` | macOS 整包发布（内置本次界面），内置已批准的桌面界面 |
| macOS 整包 | `ui`、`macos.core` | macOS 整包发布，内置该提交构建的界面 |
| iOS | `ios` | iOS 发包 |
| Android | `android` | 本地原生同步及打包 |

修复问题通常升第三段（`1.1.9 → 1.1.10`），新增兼容功能升第二段（`1.9.15 → 1.10.0`），不兼容变更升第一段（`9.12.15 → 10.0.0`）。每段按整数比较。只修改参与本次发布的字段，各端允许使用不同版本。

网页和桌面内测修复后，保留本轮版本，提交修复并新跑原工作流。首次切换分渠道时请核对旧的预留基线。iOS 同一展示版本可上传多个构建，每次上传使用新的构建号。

## 3. 谁构建、谁发布、谁决定更新内容

1. **GitHub Actions** 选择「只构建界面」「只构建桌面核心」「同时构建」。先向后端申请构建批次及版本，再按选项构建、签名、上传到 OSS 不可变路径。界面上传文件清单、摘要及签名；壳按系统和架构上传首次安装包、Updater 所需更新包及签名。macOS 面向用户发行还要处理应用签名和公证。只构建壳时，把指定的已批准界面作为随包保底界面，无需重发它的独立资源包。
2. **后端登记候选**。校验 CI 凭证、构建来源、版本、摘要、签名与目标平台；以构建批次和摘要处理重试。联合发布只有在所有要求的产物均齐备后才能确认。CI 凭证只允许登记，不能把候选设为线上版本。
3. **管理后台确认**。「应用 / 系统发布」沿用现有发布分组，默认展示当前生效组合与候选列表。点候选打开确认弹窗，显示本次实际变化、继承的另一组件、涉及平台、兼容结果、是否重启和更新说明。网页与桌面可选择发布范围；只有 macOS 包准备好时，可以明确只发 macOS，Windows 继续使用自己的已发布组合。
4. **后端发布目标组合**。以预期的当前发布编号做并发检查，避免两个管理员先后发布时把彼此的新组件覆盖回旧版。基线变化则重算并再次确认。桌面检查接口只返回已批准且适配系统/架构的组合。网页端沿用稳定的入口和 `web-version.json`；确认后才推广候选，先就绪资源，再发布入口和 worker，最后发布版本标记。OSS 和数据库无法共用一个事务，后台要记录每个渠道的推广状态，失败可按同一发布编号重试；未完成的渠道不可标成「已生效」。仅发壳时不改网页入口、worker 和版本文件。
5. **客户端执行一次计划**。请求带运行环境、平台架构、当前界面版本/摘要和核心版本。后端给出一个发布编号、一份说明、兼容的目标组合，以及该设备缺少的产物。前端只消费这份计划。桌面端由一个更新协调器负责调度签名界面更新和 Tauri Updater；浏览器/PWA 复用界面更新弹窗和现有 worker。桌面环境关闭网页的独立轮询入口，避免两个检测器各弹一次。

## 4. 组合与兼容规则

以下均以同一台机器当前运行为「界面 0.2.3、核心 1.0.0」为例。

| 已批准目标 | 桌面实际动作 | 网页/PWA |
| --- | --- | --- |
| 界面 0.2.4、核心 1.0.0 | 仅下载界面包；完整校验后切换本地目录，重载当前窗口 | 提示界面更新 |
| 界面 0.2.3、核心 1.1.0 | 仅下载与本机架构匹配的核心更新包；安装并重启，继续加载兼容的界面 0.2.3 | 无提示 |
| 界面 0.2.4、核心 1.1.0 | 两项均加入同一计划；用户确认一次，先备齐并校验两项，再安装核心；重启后启用目标界面 | 仅处理分配给网页渠道的界面版本 |
| 两者均一致 | 自动检查静默结束；手动检查显示「已是最新版本」 | 同理 |

**按每台设备的实际版本算差量。** 即使后台发布的是联合版本，一台已经装好核心 1.1.0 的电脑也只需要下载界面。跳过多个版本的设备可以直达兼容目标；存在必经的迁移版本时，后端必须给出升级路径。

界面清单声明桌面桥接协议范围及必需能力，核心清单声明支持的协议和能力。例：新界面用到了核心 1.1 才提供的文件接口，后台就不能批准「旧核心 1.0 + 新界面」这个桌面组合。可选择联合发布、只向兼容设备开放，或单独发布可在浏览器运行的网页构建。反过来，纯壳更新也要验证它仍能加载已批准的界面。相同 UI 源码可按渠道构建；浏览器包依赖 Service Worker，桌面包由 Rust 加载本地资源，分别登记摘要。

## 5. 自动检查、设置和一个进度弹窗

- 桌面首次打开先展示本机界面，随后静默检查。建议运行中每 30 分钟检查，回到前台或恢复联网时补查；自动触发合并并节流，网络错误退避。设置里的「检查更新」立即检查，与进行中的请求合并。多窗口由 Rust 侧协调，单个进程只下载一份。
- 设置 → 系统版本展示实际版本、上次成功检查时间、当前状态、「检查更新」及可用更新说明。离线显示「暂时无法检查」，保留上次检查时间。选择「稍后」后自动提示按发布编号去重；手动检查仍可打开同一更新，新发布可再次提示。
- 单个弹窗顺序为「发现更新 → 下载 → 校验 → 应用或重启 → 完成/失败」。展示一份说明和本机实际变化：仅界面显示「更新并刷新」，含核心显示「更新并重启」。「稍后」只在开始更新前提供。桌面端启动下载前先处理各窗口未保存内容。
- 已知包大小时，主进度按本机所需文件的已下载总字节 / 总大小计算，界面包与核心包按大小加权。下方列出「方舟界面」「桌面核心」各自状态。无可靠字节总量时，沿用已校验文件计数或显示阶段进度。下载达到 100% 后继续显示校验或安装，直到新版实际启动。Windows 安装器可能接管末段进度，重启后恢复同一发布记录，不再二次询问。[Tauri Updater 官方说明](https://v2.tauri.app/plugin/updater/)
- 浏览器/PWA 只比较界面版本与实际构建，其手动检查与自动检查共用同一弹窗。待办等子应用的独立版本不参与系统更新计算。

### 5.1 桌面核心下载后的自动安装与打开

含核心更新时，统一弹窗的按钮为「更新并重启」，旁边提示「更新期间暂时无法使用方舟，安装完成后将自动重新打开」。用户点一次即同意完整流程。

1. 确认更新后，原生更新协调器先冻结各窗口编辑并保存待提交内容。保存失败则恢复操作，提示处理后重试。保存成功后开始下载，直到校验、安装和切换结束，所有方舟窗口都阻止业务操作。进度弹窗持续显示，隐藏关闭和「稍后」，屏蔽 Esc、遮罩点击、窗口关闭及业务快捷键。安装器接管时允许更新流程自行退出。所需资源通过校验后，先持久化发布编号和目标版本，再交接安装。
2. 协调器将控制权交给更新器。macOS 在安装成功后由 Rust 调用 `app.restart()`。Windows 执行安装时旧进程会退出，须由安装器完成安装并启动新版。按发行包分别验证自动启动，整个流程只有一个组件负责拉起新版。[Tauri Updater 官方说明](https://v2.tauri.app/plugin/updater/)
3. 新进程自动显示主窗口，读取实际核心版本，恢复同一发布记录。实际版本匹配且界面就绪后才标记成功。若再次启动时仍是旧版，记录失败并提供重试，避免反复自动重启。

**真机验收**：从已安装的旧版发起「仅核心」和「界面＋核心」更新。点击一次后等待，确认旧进程退出、新进程自动出现且主窗口可见，设置显示目标版本；联合更新仅重启一次。用慢速下载验证 Esc、遮罩、窗口关闭、切换到另一方舟窗口均无法绕过锁定。另测下载中断和签名失败，确认任务结束后显示「重试」和「返回旧版」，返回后恢复操作。仅界面更新验证原进程持续运行、窗口重载。

## 6. 断网、失败、回滚

桌面将资源写入临时目录，校验签名和清单后原子标记为已准备；磁盘不足或下载中断时当前版本继续运行。确认安装前持久化发布编号、目标摘要、下载状态和待执行阶段。重启后先读取真实壳版本，再决定启用哪个界面。原生侧完成界面包验签，子应用无权调用系统更新命令。

联合更新期间，旧壳继续使用旧界面。新壳启动后才启用已准备好的新界面，并等待界面挂载及桥接握手成功才标记完成。失败则加载最近的兼容界面或安装包内置的保底界面；无法启动的原生二进制不能依靠界面代码自行修复，要提供已签名的修复安装包。CI 的 Updater 私钥、界面签名私钥由受保护的构建环境持有，客户端只内置验证公钥。

后台撤回发布先停止继续分发。已升级设备恢复可用界面时发布新的发布编号并显式授权已知摘要；核心修复优先用更高版本重新发布，保留 Tauri 默认的版本保护。回滚前核对本地配置和后端接口兼容性。

## 7. 建议实施顺序与验收

1. **网页版本治理**：接入构建前版本分配、设置里的「系统版本 / 检查更新」、后台候选和正式网页推广。切换时保留旧网页识别的 `web-version.json.build` 字段，让已支持检测的老客户端仍可升级。
2. **桌面端基础**：先验证 macOS 的本地启动、签名界面包、保底界面、系统版本页和自动检查，再接入核心签名更新。
3. **联合发布**：接通 GitHub Actions、OSS、后台确认、按平台解算目标及跨重启恢复。按实际支持范围补充 Windows 的安装和重启测试。
4. **发布验收**：用真实前后两个构建分别跑只发界面、只发壳、联合更新、无更新、跨版本升级；再验证断网、磁盘不足、校验失败、缺少目标架构包、同一候选重复提交、并发发布、旧设备不兼容和重启后恢复。验收结果包括一次提示、正确下载量、最多一次必要重启，以及设置里显示的实际运行版本。

### 安装完成后卡在自动重启（2026-11-28）

已确认一次真实故障：下载、签名验证和安装均成功，磁盘应用已更新，但等待旧 PID 退出的 `tbox-relaunch` 助手一直运行。原因是安装流程调用 `app.exit(0)`，而主进程在 `busy=true` 时拦截所有普通退出，两者互相等待。

修复后，只有安装成功且重启助手启动成功，才设置内部重启标记并允许本次 `Some(0)` 退出；普通关窗/退出在下载、安装期间仍被保护。阶段提示切换为「安装完成，正在重启方舟」。新增回归测试覆盖安装前拒绝退出、安装后放行及其他退出事件仍受保护。此修复需随下一版 Mac 核心发布，当前已安装的 1.0.6 不会因源码修改而自动修复。

处理旧版本卡住现场时，先核对应用包版本、更新 journal 的 pending 目标及重启助手进程，确认安装完成后再征得用户同意结束旧进程；由已有助手重启，不清空应用数据或更新 journal。重启后核对 pending 已清除、实际界面和核心版本正确。不能只凭下载 100% 就判断安装已完成并终止进程。
