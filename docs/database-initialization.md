# 数据库首次初始化

项目尚未正式部署，已将历史 TypeORM migrations 合并为一份当前完整的初始化基线 `2026-10-18.1`。不再逐条执行旧的建表、改表和数据回填，也不再使用 `schema_migrations`。TypeORM 的 DataSource、EntitySchema、Repository、事务照常使用，`synchronize` 保持关闭。

## 使用方法

在 `api/.env` 配置 MySQL 后执行：

```bash
pnpm db:init
pnpm admin:init
# 可选：创建初始普通账号和个人账本；也可以直接在前端注册
pnpm user:init
```

`db:init` 会在目标数据库不存在时创建它，再按外键依赖创建全部业务表，写入必要默认配置、系统分类和日历初始节假日。不创建演示账单、无主的“原有账本”、服务商或模型。管理员、普通用户分别由独立命令初始化，不会自动重置已有账号。

PM2 / Docker 发布入口不变：构建产物仍执行 `node dist/init-db.js`，随后执行管理员初始化和既有启动流程。数据库建议 MySQL 8.0.16+（需要 JSON、表达式默认值与实际生效的 CHECK 约束），CI 使用 MySQL 8.4。每张表都明确指定 `InnoDB / utf8mb4 / utf8mb4_unicode_ci`，不依赖服务器或预建数据库的默认排序规则。

## 旧开发库或初始化失败留下的库

**新初始化不是旧库升级脚本，也不会自动删表、清库或重建已有数据。** 发现没有本次初始化标记的已有表时，脚本在写入之前停止并说明原因；旧 `schema_migrations` 不会被当作新基线。

最简单的办法是在 `api/.env` 将 `MYSQL_DATABASE` 改为一个尚不存在的数据库名，例如 `t_box_dev_v2`，再执行 `pnpm db:init`。原库保留，可以随后自行核对、备份和清理。服务器若只是首次部署失败，也可以先备份核对，再由操作员清空确认无用的库；程序不会替你执行这一操作。只删除 `schema_migrations` 不能修复旧表结构。

已有开发数据如果要继续使用，需要单独的数据迁移方案，不能通过首次初始化直接接管。

## 重复执行与故障恢复

- `schema_initialization` 保存基线版本、结构指纹和初始化状态。完成后重复运行只确认版本及业务表是否齐全，不重写配置、分类、充值套餐或其他数据。
- 初始化先获取当前数据库专属的 MySQL 命名锁；两个进程同时运行不会重复写入默认数据。
- MySQL DDL 自动提交，初始化标记会先保存。中途失败后，同一基线可直接重跑；建表使用 `IF NOT EXISTS`，全部默认数据和完成标记在同一事务提交。
- 指纹不匹配或完成后丢表时明确报错，不以“初始化成功”掩盖结构不一致。不要手动修改初始化标记绕过检查。

## 代码归属与后续版本

`api/src/db/initialize.ts` 负责通用初始化流程，`api/src/db/schema/` 保存平台各模块表定义。应用表和默认数据分别保存在 `apps/ledger/server/src/schema.ts`、`apps/calendar/server/src/schema.ts`、`apps/time/server/src/schema.ts`，由 API 组合入口统一注册；AI 模块不负责应用建表。

**正式部署后必须保留已发布基线。** 后续表结构变化要新增明确的增量升级脚本及版本记录，不能再次删除历史或修改已发布初始化来更新线上库。结构指纹会阻止误用不同的基线。

## 验证

```bash
MYSQL_DATABASE=t_box_test_init pnpm test:db-init
```

测试连接账号需要创建、删除测试数据库的权限。测试使用随机命名的临时数据库并在结束后清理，覆盖异构默认排序规则、完整建表与默认数据、重复运行、用户/账本创建、中断恢复、旧库保护和并发初始化，不修改个人业务库。
