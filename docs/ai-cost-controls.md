# AI 成本与服务商并发

后台「配置中心 → 成本与并发」管理以下数据库配置，沿用 Redis 缓存及 revision 失效；新请求读取。所有金额单位为人民币元，0 关闭对应限额。

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| ai.cost.taskYuan | 20 | 单任务累计成本上限 |
| ai.cost.userDailyYuan | 100 | 单用户北京时间自然日成本 |
| ai.cost.platformDailyYuan | 1000 | 平台北京时间自然日成本 |
| ai.provider.concurrency | 8 | 同一个服务商同时运行的模型/图片请求数 |
| ai.provider.queueTimeoutMs | 30000 | 并发满时最多排队毫秒数 |
| ai.routing.cooldownBaseMs | 5000 | 服务商失败后模型冷却起点 |
| ai.routing.cooldownMaxMs | 60000 | 模型冷却上限 |

服务商可单独设置总并发上限（0 跟随全局默认值），每个模型另设并发上限（默认 4），同时满足两层限制才发出请求。同用途模型池会按负载轮换分配新任务，详见 [模型池与任务审计](ai-model-pools.md)。

恢复进程并发 `ai.worker.concurrency` 默认 2，限制单恢复进程；服务商槽位和成本预算由 MySQL 在所有 API/worker 进程之间共享，不能依靠每个进程自己的计数器。

请求进入服务商队列时不预留钱包；获得槽位后，用短事务串行校验任务、用户日和平台日预算，再登记此次成本预估与钱包预留。并发请求不能同时越过同一剩余额度。额度用尽返回明确错误，不派发上游请求。服务商槽位带 90 秒租约、25 秒续约，取消/完成释放；执行者失去租约会中止当前请求。崩溃后槽位到期回收。

`cost_reserved_micro` 独立于钱包预留。record_only 用户不扣余额，但实际调用仍占成本预算。已完成请求使用实际用量计价；缺少 usage、结果待核对、管理员解除用户钱包预留等情况，都不能把平台成本清零，预算保守保留预估/已知费用的较大值。迁移前未留下预估的旧 record_only 请求无法凭空还原成本。

标题生成不扣用户余额，但记录 purpose=title 的用量/成本，参与成本预算与共享并发。上下文整理、分析、结果核对和图片同样按真实调用记录，不能只统计最终回答。

这里的“成本”按后台配置的模型价格计算。如果后台填写的是对用户售价，它并不等于服务商发票成本；不要将当前预算报告当作上游账单的精确财务对账。输入量估计也不是精确 tokenizer，用于保守准入；结算以服务商实际 usage 为准。

数据库集成测试覆盖并发准入、record_only、未知费用、免扣费标题、服务商共享槽位、排队超时与取消；不调用付费模型。
