# 会话用量与上下文管理

## 数据与职责

每个 assistant 消息的 `usage.calls` 保存本次消息中所有普通调用、专业 Agent 调用及上下文压缩调用。每条记录包含调用 ID、Agent ID、purpose、输入 / 输出 / 缓存读取 / 缓存写入 / 推理 token、耗时。消息汇总输入、输出和 total；缓存与推理分别是输入、输出的子集，不再加入 total。上游没有返回的细分字段保留 null，不猜测缺失数据。消息界面不再显示 token 数与调用次数，数据仍用于计费与审计；底部展示独立的执行用时。

`billing_usage` 用 message_id、task_id、agent_id 关联费用；每次调用保存模型配置 ID、价格和用户扣费模式快照、实际 usage、上游 response_id。公开消息和用户费用接口不返回模型配置、服务商、单价或 response_id。标题生成直接绕过用户收费入口；压缩调用有服务商消耗，纳入消息和使用费用记录。

Provider 提供通用 onUsage 回调，计费装饰器先持久化实际用量和费用，编排层再把公开统计写入消息、任务检查点及会话档案，并发出 `message.usage` socket 事件。已知用量超出余额而待核对时仍保留消息统计。最终快照和历史恢复包含这些统计，不依赖浏览器累加 delta。用量统计不包含原始思维链；公开过程使用独立分析、执行、核对阶段的行动说明，不展示隐藏推理。

## Agents SDK 与缓存的区别

[Agents SDK Sessions](https://openai.github.io/openai-agents-js/guides/sessions/) 提供会话存储接口和 Responses 压缩包装器，底层压缩仍需服务商支持 `/responses/compact`。它不会替任意兼容服务商提供模型缓存，也不能代替应用自己的资源权限、任务租约、工具幂等和资金事务。

项目继续使用已有的通用 Agent 运行循环；不为了压缩引入另一套 Runner 覆盖已经实现的断点、前端工具、私有认证和恢复机制。上下文准备在 `agent/context.ts`，OpenAI 接口在 `chat/provider.ts`，计费在 `billing/provider.ts`，附件字节还原在资源模块，应用业务留在各自模块。

[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) 发生在服务商；缓存命中以 usage 为准，不承诺缓存键必然命中。不同模型的缓存长度、时长、写入策略和成本可能不同，不能统一假设缓存免费。本项目记录 cached_tokens 与 cache_write_tokens；用户售价仍沿用后台配置的统一输入 / 输出价，不冒充服务商成本对账，也不自动按某个服务商的折扣调整用户售价。

## 已实现的优化

完整的现行策略见 [会话历史与上下文整理](chat-context.md)，包括当前会话历史、工作记忆持久化、最近四轮保留、执行中压缩、75% 触发比例、重复压缩抑制、通用事实摘要/原生压缩/关闭三种模式、分段大小约束、时间线与失败恢复。

- 工具按名称稳定排序、技能按需激活、专业 Agent 独立上下文；缓存键仅在服务商支持时开启。
- 新模型输入预算默认 98304，旧预算保留；输出默认推理模型 32768、普通模型 8192，可由后台调整。已知总窗口自动扣除输出空间和安全余量，未知窗口必须按服务商实际限制配置。
- 通用事实摘要不要求 `/responses/compact`；原生模式保留服务商加密记忆。最近原文/调用对保留，最新请求本身超大时明确报错。
- 可选 `/responses/input_tokens` 精确计数；默认保守估算，实际收费仍以 usage 为准。
- 原始消息、工具回执、权限、解锁授权、幂等记录与写入日志独立保留，不由摘要取代。
- 附件在请求前解析，整理后还原为 asset / asset-text 引用，禁止把私有 base64 持久化进工作历史。

## 使用与限制

后台「模型 → 编辑」配置输入/输出预算、总窗口和压缩方式。摘要默认为推荐模式，原生压缩、精确计数、缓存键须确认服务商接口支持；事实摘要支持 Responses 与 Chat Completions。Chat Completions 自动使用保守估算，不能开启 Responses 专用的精确计数与原生压缩。

当前没有跨会话长期记忆、向量检索或自动 RAG；账户、账本和任务业务状态通过授权工具读取，不批量塞入提示词。新的 GPT 模型缓存 breakpoint / TTL / explicit mode 不自动套到所有服务商；需要确认模型能力后再扩展策略。压缩可能降低下一轮缓存命中，应比较总体 token、实际成本和延迟，而不是只追求命中率。

输出/推理上限由模型预算控制，预留仍是保守入场预算，最终按真实 usage 结算，超出余额会进入待核对。未返回 usage 的收费调用继续沿用待核对机制，不能靠本地估算扣款。

`pnpm test` 覆盖 SDK 用量、缓存读写、压缩、工具配对和附件还原；`pnpm test:billing` 验证消息 / 任务费用关联与压缩计费；`pnpm test:presentation` 验证 socket 用量和历史恢复。测试不请求真实模型。

`pnpm test:context` 验证执行中压缩、独立回执核对、分段收费、暂停续跑和持久化会话恢复。
