# 按需能力发现与上下文管理

## 应用与 AI 的边界

应用继续通过独立 `ApplicationModule` 声明工具、技能、专业 Agent、导航、权限、确认和业务处理器。应用不引用宿主 AI Runner，也不需要把自己的工具录入管理后台。新增应用仍通过组合根注册；AI 通用层不包含应用 ID、业务字段、记账/日历/图片判断分支或关键词意图路由。

宿主负责能力索引、按需加载、阶段编排、作用域、模型路由、上下文和持久化。`capability-loading.ts` 管检索与预算，`capability-tools.ts` 提供宿主工具，`tool-results.ts` 管模型回执视图与分页；业务逻辑仍留在 `apps/`。

## 每轮实际流程

1. 新任务的能力加载集合为空，初始只开放固定数量的宿主发现/历史工具。规划 Prompt 不注入整个应用、技能、专业 Agent 和业务工具目录。
2. 普通问答可以在第一次请求直接回复。需要能力时，由模型根据语义提炼检索词，调用 `capability_search`；不是后端用业务关键词猜测用户意图。
3. 搜索只遍历当前用户可用、已安装且位于当前 Agent 作用域内的声明。返回有限候选的名称、描述、应用、技能和专业 Agent 元数据，不返回处理器或私有 Prompt，并在预算内自动加载候选。
4. 模型可改写检索词；空 `query` 加 `appId` / `offset` 可分页浏览，避免一次检索遗漏就误判不支持。已知确切工具名可用 `capability_load` 直接加载。默认实现为声明元数据的文本检索，不声称已经接入向量语义索引。
5. 确定能力后提交 `workflow_plan`，进入执行阶段才开放已加载业务工具的完整 Schema。检索/加载与阶段决定不能混在一个批次；它们不会执行业务处理器。
6. 只启用所加载工具的所属技能；不因一个技能包含几十个工具就全部开放。整套技能超出预算时，返回明确提示，保留原加载集合。加载新定义会按加载顺序淘汰较早定义及不再使用的技能指导；执行记录不删除，后续可重新加载。
7. 专业 Agent 只继承属于自身作用域的已加载工具定义和技能，仍保留独立对话历史。其余主会话历史不开放给委派 Agent；主助手的公开历史读取工具也不授予专业 Agent。

应用可以只提供工具，不必为接入 AI 强制实现技能或专业 Agent。需要技能指导时，其工具分组仍由应用自己声明；宿主可对一个大技能只开放少量工具。如果技能指导本身过长，应用作者需要按功能拆分技能，宿主不会擅自截断业务/安全指导。

## 固定预算与动态导航

配置项通过现有后台 AI 配置管理，入 MySQL，沿用 Redis 缓存、修订记录和任务快照。应用业务配置和工具定义不进入此配置表。

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `ai.tools.maxLoaded` | 16 | 单 Agent 同时加载的业务工具数量，不含固定宿主工具 |
| `ai.tools.maxSchemaBytes` | 32768 | 业务 Schema 总字节预算 |
| `ai.tools.maxInstructionBytes` | 16384 | 活动技能指导总字节预算 |
| `ai.tools.searchPageSize` | 6 | 每页最多搜索候选数，超预算候选不强行加载 |
| `ai.tools.maxApplications` | 8 | 同时加载的应用及近期目录上限 |
| `ai.tools.discoveryRounds` | 12 | 单 Agent 发现/补读轮数，仍受任务总轮数上限约束 |
| `ai.context.toolResultBytes` | 12288 | 模型单条工具回执大小预算 |
| `ai.context.summaryMaxParts` | 8 | 一次原子摘要最多分段数量 |
| `ai.routing.conversationAffinity` | true | 同会话优先健康且未满载的原模型 |

业务 Schema 和活动技能指导各自还受当前模型有效输入预算四分之一的动态限制。计数/长度超限不通过裁剪 Schema、删参数或截断指令解决，模型需减少加载数量；单个定义过大需由应用作者优化或调整相应预算。

`app_open` 仅携带当前已发现应用的导航参数 Schema。不会将所有应用的 `anyOf` 发给模型，也不会先深复制整个导航目录再丢弃。专业 Agent 的应用/技能枚举同时按作用域裁剪。

安装可见性在一次编排迭代内复用，跨迭代重新查询；实际执行、恢复与结果读取仍重查安装版本、身份和资源授权。加载状态不是授权凭据。

## 大结果和原文补读

完整工具回执继续保存在后端执行日志和会话记录中。模型工作历史内的大回执使用显式 `truncated`、有限预览和 `resultRef: { callId, path }`。前端状态、必需工具成功检查、写入幂等和恢复均使用完整回执，不依赖预览。

`tool_result_read` 使用 JSON Pointer 路径、`offset`、`limit` 分页读取已存在的结果。嵌套的大对象继续提供子路径引用；读取长字符串和列表同样受大小限制。读回执不重新执行原工具，不能读取内部配置型工具的旧回执，也不能跨越当前专业 Agent 的工具/应用作用域。按来源消息的资源引用重查读取权限，不重放原工具的写入参数解析；来源消息已删除时不能继续读取缓存回执。

`conversation_history_read` 只检索当前会话的公开原始消息，支持关键词和消息游标分页。不会读取其他会话、内部模型历史、摘要正文、隐藏推理或私有 Prompt。长消息带有明确截断标记及 `contentRef`；模型可用 `messageId`、`offset` 按 Unicode 字符分段补读完整原文。

## 模型保持与滚动摘要

新会话按共享负载和轮换顺序分配模型；同会话的新任务优先使用仍在池内、健康且有容量的原模型。原模型冷却、满载、停用或移出池时，新任务可切换。正在执行/恢复的任务仍严格绑定原配置，不在收费调用或工具循环中途切换。

切换时保留可移植的事实摘要和完整工具调用配对，清除旧 Provider 的推理、消息 ID 和私有状态。存在不可迁移的原生加密压缩项、私有 item 引用等状态时，才从原始会话与真实回执重建。重置的是旧预算的压缩抑制基线，不是无条件丢弃文本记忆。

每次模型调用前检查上下文，包括发现、分析、工具循环、核对、最终回复和专业 Agent。超过触发比例后，保留近期原文和完整工具配对，对早期部分分段合并；上一份摘要作为 `previousMemory` 合并新事实，避免反复从全部原始历史开始。摘要需保留资源和回执引用、最新更正、未完成与不确定状态。

所有分段成功并通过大小/压缩效果检查后才替换工作历史。失败不损坏原上下文；分段请求仍通过原来的最多五次可恢复错误重试和独立用量记录。前端按时序显示「整理上下文」的开始、分段和完成状态，处理中显示「正在整理上下文…」，最终成功回复后折叠之前的处理过程；不向用户展示内部摘要内容。

输入估算只统计实际发送的 `history`、`tools`、`instructions` 与图片安全余量，不把后台配置快照、审计标识、保密比对材料重复算成模型输入。估算不等于 tokenizer 或收费 usage；计费仍以服务商实际用量为准。

## 兼容与测试

正式 API 组合根默认启用 deferred 模式。已有任务检查点没有 `capabilityLoading` 标记时保持原工具协议，防止升级改变暂停任务的行为；新任务重新按需发现。直接嵌入 `ChatService` 的自定义宿主可显式设置 `capabilityLoading: 'deferred'`，旧嵌入式宿主默认保留兼容行为。

`api/test/capability-loading.test.ts` 覆盖 1600 工具初始上下文不增长、搜索分页、加载/指令预算、作用域、安装撤销、导航裁剪、回执补读、公开历史、滚动摘要、模型迁移和完整阶段循环。`api/test/capability-loading.integration.ts` 使用隔离 MySQL 与假模型验证检查点、完整回执和重启续办；模型池集成测试验证健康会话保持、满载/移出池切换及严格恢复绑定。不请求真实付费模型。

设计参考：[OpenAI 按需工具搜索](https://developers.openai.com/api/docs/guides/tools-tool-search)、[上下文压缩](https://developers.openai.com/api/docs/guides/compaction)。本实现采用宿主通用函数协议，兼容已接入的 Responses 和 Chat Completions，不要求服务商支持原生 tool search。
